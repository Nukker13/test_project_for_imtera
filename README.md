# Парсер отзывов из Яндекс.Карт

Веб-приложение, которое принимает ссылку на карточку организации в Яндекс.Картах, вытягивает оттуда отзывы и показывает их с пагинацией, средним рейтингом и раздельными точными счётчиками оценок и отзывов.

**Стек:** Laravel 13 + Sanctum · Vue 3 (Composition API) · Python (curl_cffi + Patchright) · PostgreSQL · Redis · Docker Compose.

Проверено на реальной карточке `https://yandex.com/maps/-/CTxMzF5W` (Hummus Kimchi, Ереван): собрано **172 из 172 отзывов**, 477 оценок, средний рейтинг 5.0.

---

## Как поднять локально

Нужен только Docker.

```bash
docker compose up --build
```

Поднимутся шесть сервисов: `app` (Laravel, :8000), `frontend` (Vite, :5173), `python-service` (парсер, :8001), `db` (PostgreSQL), `redis`, `queue-worker`.

Миграции и сид выполняются автоматически при старте `app`, отдельных команд запускать не нужно. Первая сборка занимает несколько минут — в образ парсера ставится браузер.

Откройте **http://localhost:5173** и войдите:

| Поле | Значение |
|---|---|
| Email | `admin@imtera.test` |
| Пароль | `password` |

Дальше вставьте ссылку на карточку организации (короткие ссылки вида `/maps/-/XXXX` тоже работают) и нажмите «Собрать отзывы».

### Проверка парсера отдельно

Самый быстрый способ убедиться, что обход защиты работает, — запустить парсер без Laravel и очереди:

```bash
docker compose exec python-service python scripts/try_parse.py "https://yandex.com/maps/-/CTxMzF5W"
```

Тесты алгоритма подписи:

```bash
docker compose exec python-service python -m pytest tests/ -q
```

## Обоснование выбора алгоритма

### Что было в ТЗ и что показала практика

ТЗ описывало схему: **Patchright открывает страницу → отдаёт cookies и токены в curl_cffi → curl_cffi делает прямые запросы к `fetchReviews`**.

При реализации выяснилось, что первая половина схемы работает наоборот. Замеры по тестовой карточке:

| Клиент | Результат на странице организации |
|---|---|
| Patchright (headless chromium) | тело `limited`, 158 байт — antibot-заглушка |
| Patchright + прогрев сессии на `yandex.ru/maps` | то же `limited` |
| Patchright на `yandex.ru` и на `yandex.com` | то же `limited` |
| **curl_cffi, `impersonate="chrome"`** | **HTTP 200, ~1 МБ, со `state-view` и `csrfToken`** |

Egress-IP у контейнера и у хоста одинаковый, так что дело не в IP: браузер отсекается именно по совокупности признаков автоматизации. Под `linux/arm64` (Apple Silicon) настоящего Google Chrome не существует, а патченный chromium Patchright всё ещё отличим; curl_cffi же воспроизводит TLS/JA3-отпечаток Chrome точно и проходит.

Поэтому **основным путём получения сессии сделан HTTP**, а Patchright сохранён как фолбэк — ровно в той роли, что описана в ТЗ: если HTTP упирается в блокировку, браузер исполняет JS-челленджи, формирует сессию и передаёт cookies обратно в curl_cffi.

### Что понадобилось, чтобы `fetchReviews` вообще ответил

Эндпоинт не документирован, и к данным ведут три двери, каждая из которых была найдена экспериментально:

1. **TLS-отпечаток.** `requests`/`httpx` с идеально подобранными заголовками отсекаются на рукопожатии. Нужен именно curl_cffi с `impersonate="chrome"`.
2. **Подпись `s`** — djb2-xor хэш от query-строки с ключами, отсортированными по алфавиту (`h = h * 33 ^ c`, начальное 5381, результат как uint32). При неверной подписи Яндекс отвечает голым `Bad Request` без пояснений.
3. **Обновление `csrfToken`** — главное недостающее звено. Токен со страницы Яндекс считает просроченным: на первый запрос он отвечает `{"csrfToken": "<новый>"}` **вместо данных**, и запрос нужно повторить с выданным токеном. Без этого цикла прямые запросы не работают вообще, сколько бы правильной ни была подпись.

Плюс обязательный параметр `locale=ru_RU`, без которого приходит `Validation error. "query.locale": Required`.

Итоговый запрос:

```
GET https://yandex.ru/maps/api/business/fetchReviews
    ?ajax=1&businessId=<oid>&csrfToken=<свежий>&locale=ru_RU
    &page=1&pageSize=50&ranking=by_time&sessionId=<sid>&s=<подпись>
```

### Сравнение с альтернативами

| Вариант | Почему не он |
|---|---|
| Официальное API Яндекс.Карт | Отзывы организаций через него не отдаются вообще. |
| `requests` / `httpx` + подмена User-Agent | Отсекается по TLS-отпечатку ещё до обработки заголовков. |
| Чистый headless-браузер со скроллом | Работает, но медленно и тяжело: 600 отзывов — это десятки итераций скролла против 12 HTTP-запросов, плюс браузер в этом окружении сам упирается в `limited`. Оставлен как фолбэк. |
| Парсинг HTML карточки | Отзывы подгружаются лениво, в исходном HTML их нет; и разметка меняется куда чаще, чем JSON-контракт. |
| **curl_cffi + подпись + цикл CSRF** | Выбран: 12 запросов вместо десятков действий, точный JSON вместо вытаскивания текста из вёрстки. |

**Чем платим:** подпись `s` и поведение CSRF реверс-инженерены и могут измениться в любой момент. Ровно поэтому в проекте есть браузерный фолбэк и трёхуровневый детект поломки — см. ниже.

### Почему не добираем больше ~600 отзывов

Яндекс отдаёт максимум ~12 страниц по 50 на один режим сортировки. Формально лимит обходится дополнительными проходами по `by_rating` / `by_relevance` с дедупом по `reviewId`, но это втрое больше запросов и втрое выше риск словить капчу. Сознательно ограничились одним проходом `ranking=by_time`: требование «до 600 штук» он покрывает полностью. Если собрано меньше, чем Яндекс заявляет в `data.params.count`, интерфейс честно показывает оба числа.

## Как парсер понимает, что он сломался

Молчаливая деградация — худший сценарий для парсера: он возвращает пустой список, а система считает, что у организации просто нет отзывов. Поэтому проверок три, на разных уровнях.

**1. Якорные структуры.** Нет блока `state-view`, он не разбирается как JSON, в нём нет `csrfToken` или не удалось определить `businessId` → `LAYOUT_CHANGED`. Метаданные ищутся не по жёстким путям вида `data.ctx.business.rating.score`, а поиском по дереву с набором синонимов ключей — это переживает перестановку блоков и падает только при реальном переименовании полей.

**2. Схема данных.** Каждый отзыв обязан дать `id`, оценку в диапазоне 1–5, автора и разбираемую дату. Отдельные кривые записи — нормальная жизнь, но если схему не проходит больше 40 % выборки, формат поехал целиком → `LAYOUT_CHANGED`.

**3. Санити-чек.** Яндекс сообщает о N отзывах, а собрано 0 → это поломка, а не пустая организация → `LAYOUT_CHANGED`. И отдельно: если у организации нет ни адреса, ни рейтинга, ни оценок, ни единого отзыва — это не «организация без отзывов», а признак того, что открыта не та страница → `ORG_NOT_FOUND`.

**Отдельный случай: несуществующая организация.** Яндекс не отвечает ошибкой на неизвестный идентификатор — по адресу `/maps/org/<любое число>/reviews/` он отдаёт обычную страницу карт со статусом 200. Без проверки парсер заводил бы организацию с названием «Карты» и нулями вместо отказа. Ловится по двум признакам: идентификатор берётся **только** из конечного адреса редиректа (искать `oid` по телу страницы нельзя — на общей странице карт в выдаче попадаются чужие организации), а сама страница проверяется по `canonical`: настоящая карточка канонизируется в собственный `/maps/org/...`, подменная — в корень `/maps/`.

Отдельно стережётся самое хрупкое место — подпись. `fixtures/real_request.json` хранит реальный запрос, а `calibrate()` проверяет, какая схема канонизации его воспроизводит. Если ни одна — `SIGNATURE_MISMATCH`, и это видно сразу, а не в виде необъяснимых отказов.

### Коды ошибок

| Код | Когда | Что происходит дальше |
|---|---|---|
| `INVALID_URL` | ссылка не на карточку Яндекс.Карт | отказ сразу, до постановки в очередь |
| `ORG_NOT_FOUND` | карточка не существует, ссылка битая или устарела | прогон `failed`, организация в базе не заводится |
| `BLOCKED_CAPTCHA` | капча, `403`, `429`, тело `limited` | фолбэк на браузер, при неудаче `failed` |
| `SIGNATURE_MISMATCH` | подпись больше не принимается | фолбэк на браузерный скролл |
| `LAYOUT_CHANGED` | разметка/формат изменились | `failed` сразу — фолбэк упрётся в то же самое |
| `UPSTREAM_TIMEOUT` | Яндекс не ответил | фолбэк, при неудаче `failed` |
| `PARSER_UNAVAILABLE` | Python-сервис не отвечает | `failed` |

Деградация двухступенчатая: сначала на уровне сессии (HTTP заблокирован → страницу открывает браузер и отдаёт cookies в curl_cffi), затем на уровне сбора (прямые запросы не работают → отзывы собираются скроллом, подпись не нужна вовсе). Когда данные получены обходным путём, прогон помечается `degraded`, и интерфейс показывает это отдельной плашкой — результат не выдаётся за обычный успешный.

**Автоматических ретраев нет** (`$tries = 1`). При неудаче пользователь видит причину человеческим текстом и сам решает, повторять ли. Автоповтор после бана только усугубил бы блокировку.

## Как работают очереди

Сбор 600 отзывов — это десяток последовательных запросов с паузами, то есть минуты. Держать на это открытым HTTP-соединение с браузером нельзя, поэтому:

```
POST /api/organizations
   └─ создаёт parse_run (status=pending), ставит job в Redis, отвечает 202 + run_id
        │
        ▼
   queue-worker (отдельный контейнер)
        ├─ status=running
        ├─ HTTP-запрос к python-service (таймаут 600 с)
        ├─ ReviewsUpsertService раскладывает результат по таблицам
        └─ status=success | failed + код ошибки
        │
        ▼
   фронтенд опрашивает GET /api/parse-runs/{id} раз в 2 с до терминального статуса
```

Воркер вынесен в отдельный контейнер сознательно: парсинг долгий и не должен конкурировать с обработкой веб-запросов. Python-сервис своей очереди не имеет и остаётся синхронным — очередь уже есть на стороне Laravel, вторая была бы лишней сущностью.

## Идемпотентность и модель данных

```
organizations                     reviews                        parse_runs
─────────────────                 ─────────────────              ─────────────────
id                                id                             id
yandex_permalink  UNIQUE  ◄────┐  organization_id ──┘             organization_id
url                            │  yandex_review_id                url
name, address                  │  ├─ UNIQUE(organization_id,      status
rating_avg                     │  │         yandex_review_id)     strategy_used
ratings_count                  │  author_name, rating             session_source
reviews_count                  │  text, reviewed_at               degraded, fallback_reason
last_parsed_at                 │                                  pages_fetched
                               └──────────────────────────────────reviews_fetched
                                                                  error_code, error_message
                                                                  started_at, finished_at
```

Идемпотентность держится на двух уникальных ключах:

* `organizations.yandex_permalink` — организация заводится один раз, повторный парсинг обновляет её через `updateOrCreate`;
* `UNIQUE(organization_id, yandex_review_id)` — отзывы пишутся через `upsert`, конфликт означает тот же отзыв (возможно, отредактированный автором) и обновляет содержимое.

Проверено: три прогона по одной ссылке → `organizations = 1`, `reviews = 172`, `parse_runs = 3`.

**Про снимки.** Полной версионной истории нет осознанно. Данные организации и отзывов живут в одном актуальном экземпляре, а след каждого запуска остаётся в `parse_runs` — когда, каким способом, сколько собрано, с какой ошибкой. Этого достаточно, чтобы ответить на вопрос «почему данные такие», без дублирования всей выборки на каждый прогон. Перепарсинг только ручной: пользователь повторно отправляет ту же ссылку, никакого cron.

`ratings_count` и `reviews_count` — два независимых поля, как требует ТЗ: оценку ставят молча, отзыв пишут текстом, и числа почти всегда расходятся (477 против 172 на тестовой карточке). Отдельно показывается `stored_reviews_count` — сколько реально лежит в базе, чтобы разрыв с лимитом источника был виден.

## Масштабируемость

**Где узкое место.** Не Laravel и не БД, а внешний источник: Яндекс терпит ограниченную частоту запросов с одного IP. Вертикальное масштабирование воркеров упирается в бан раньше, чем в CPU.

**Что уже заложено.** Очередь Redis разводит прогоны по времени; воркер отдельным контейнером и масштабируется независимо (`docker compose up --scale queue-worker=N`); Python-сервис без состояния, за ним можно поставить несколько реплик.

**Что делать при росте нагрузки:**

1. **Рейт-лимит на домен, а не на воркера.** Общий счётчик в Redis: не больше N запросов к Яндексу в минуту суммарно по всем воркерам. Иначе `--scale` линейно увеличивает риск бана.
2. **Отдельная очередь под парсинг** с ограниченным числом воркеров, чтобы тяжёлые прогоны не вытесняли быстрые задачи.
3. **Пул браузерных контекстов** в Python-сервисе вместо запуска браузера на каждый фолбэк — сейчас холодный старт стоит несколько секунд.
4. **Кэш результата по `businessId`** с TTL: повторный запрос той же карточки в пределах часа не должен идти в Яндекс.
5. **Инкрементальный сбор:** зная `reviewed_at` самого свежего сохранённого отзыва, можно останавливать проход на первой уже известной странице вместо полного перебора.

## Защита от бана Яндекса

### Что реализовано в коде

* **Паузы с джиттером** между страницами (400–1200 мс, настраивается через `PARSER_DELAY_MIN_MS` / `PARSER_DELAY_MAX_MS`). Джиттер важен: ровный интервал сам по себе является признаком автоматизации.
* **Одна сессия на прогон** — cookies и отпечаток не мешаются между карточками.
* **Точный отпечаток Chrome** через curl_cffi, без рассогласования: User-Agent не переопределяется вручную, его выставляет сам `impersonate`, иначе заголовок и TLS-рукопожатие противоречат друг другу — классический способ спалиться.
* **Минимум запросов:** один проход `by_time`, ранний выход при достижении `data.params.count`, отказ от добора по другим сортировкам.
* **Распознавание бана** как отдельного состояния: тело `limited`, капча, `403`/`429` → `BLOCKED_CAPTCHA` с понятным текстом, а не безликая ошибка.

### Что задокументировано, но сознательно не реализовано

В рамках срока не делалось; вот как это выглядело бы в продакшене.

**Ротация прокси.** Пул резидентных прокси, выбор по принципу «наименее недавно использованный», привязка прокси к `businessId` на время прогона (смена IP в середине сессии сама по себе подозрительна). Прокси, получивший бан, уходит в карантин с экспоненциальным бэкоффом.

**Ротация User-Agent.** Только согласованно с `impersonate` в curl_cffi: UA обязан соответствовать TLS-отпечатку. Ротация «просто строки UA» при фиксированном отпечатке делает клиента заметнее, а не незаметнее.

**Троттлинг под нагрузкой.** Общий для всех воркеров счётчик в Redis (скользящее окно) + адаптивное замедление: после каждого `429` интервал растёт, после серии успехов медленно возвращается к норме.

**Что делать, если забанили:**

1. Пометить прогон `BLOCKED_CAPTCHA` и не ретраить автоматически — это текущее поведение.
2. Увести IP в карантин, перевести последующие прогоны на другой прокси.
3. Деградировать в браузерную стратегию: у неё другой профиль трафика и она иногда проходит там, где прямые запросы уже отбиты.
4. При массовом бане — остановить очередь и уведомить оператора, а не молотить в закрытую дверь.

## Потенциал развития

* **Автотесты.** Сейчас покрыт только алгоритм подписи. Просятся: фикстуры ответов `fetchReviews` для нормализатора, тесты идемпотентности upsert, feature-тест цикла «отправил ссылку → прогон → отзывы».
* **Версионные снимки** — отдельная таблица с историей изменения рейтинга и счётчиков, чтобы строить динамику во времени.
* **Инкрементальный парсинг** по дате последнего сохранённого отзыва вместо полного прохода.
* **Добор сверх лимита** через несколько сортировок с дедупом — когда важнее полнота, чем скорость и риск.
* **Мониторинг здоровья парсера:** доля `degraded` и `LAYOUT_CHANGED` за период — ранний сигнал, что Яндекс что-то поменял, до того как всё встанет.
* **Вебхуки** вместо поллинга статуса.
* **Расширение данных:** фотографии, ответы бизнеса, реакции, теги и аспекты — всё это уже приходит в ответе `fetchReviews`, но сейчас не сохраняется.

Логика работы с Яндексом целиком заключена в `parser/` — Laravel знает только контракт «отдай ссылку, получи организацию, отзывы и метаданные» и не содержит ни одного знания об эндпоинтах, подписи или разметке.
