Тестовый проект "Парсер из карточек в Яндекс.Карты" для собеса в Imtera

Стек:
-Backend: Laravel, Sanctum
-Frontend: Vue 3

Структура:
Две страницы: 1) логин 2) настройки организации + вывод данных

Логин происходит через seed user, реальная аутентификация не требуется

Настройки — поле для ссылки на карточку в Яндекс.Картах. При обработке ссылки происходит ее валидация, заведение entry в базе данных

Вывод данных:

- все отзывы по карточке (работодатель говорит, что там 600 штук максимум. Тем не менее, все эти 600 шт. надо вытянуть)
- Постраничная навигация по 50 отзывов на страницу
- средний рейтинг компании из Яндекс.Карт
- количество оценок и количество отзывов. Важно: эти данные должны выводиться отдельно и в виде точных чисел.
- далее — каждый отзыв отдельно с указанием даты, текста, оценки и автора.

Парсер:
- должен принимать ссылку на любую организацию в Яндекс.Картах
- доставать все доступные отзывы (помним пункт про лимит в 600 шт.)
- данные достаются поэтапно, по 50 или 100 штук за раз, чтобы не ударяться в лимиты. Очередь можно реализовать в виде queue или jobs. Вероятно через Redis, но можно рассмотреть и прочие варианты
- если парсятся данные об организации, которая уже присутствует в бд, то не нужно создавать дубликат, лучше обновить данные. Нужно продумать реализацию снимков (я тут не очень хорошо знаю опции)
- не придумывать данные, а именно подтягивать их из карточки
- ВАЖНО: обходит защиту яндекс от ботов.
- логика парсинга и работы с внешним источником вынесена из контроллеров/сервисов/фасадов/классов-оберток
- В случае отсутствующих данных/блока или смены разметки парсер должен сообщать об ошибке


Алгоритм работы:

[1. Playwright / Patchright] ──► Заходит на страницу организации
├─► Проходит начальные JS-челленджи
├─► Формирует свежую сессию (Cookies)
└─► Перехватывает свежий csrfToken и sessionId из сетевых запросов
│
▼
[2. curl_cffi (Python)]      ◄── Передает полученную сессию и токены в HTTP-клиент
│
├─► Делает прямые запросы к fetchReviews (page=1, page=2...)
├─► Пробивает TLS-защиту через impersonate="chrome120"
└─► При необходимости меняет фильтры (1-5★)
│
▼
[Отзывы сохранены в JSON/БД]

Прочие требования:

- осмысленная обработка ошибок, ошибки ясно дают понять в чем проблема.
- Vue 3, Composition API, состояние загрузки и ошибки видно в интерфейсе
- Понятная структура БД с миграциями
- проект собирается через docker-compose, работает из контейнера

## Уточнения по итогам интервью (2026-09-15)

### Приоритеты и сроки

- Дедлайн — фактически "завтра" (в ТЗ формулировка 1-3 дня, проект взят 2026-09-14). Времени мало.
- Ключевой фокус тестового задания — реальный рабочий обход антибот-защиты Яндекс.Карт (связка Playwright/Patchright → curl_cffi). Именно на нём сосредотачиваемся в первую очередь, остальные части проекта — приоритет ниже, при нехватке времени можно упростить.
- Тестовая карточка организации для разработки/проверки парсера: `https://yandex.com/maps/-/CTxMzF5W`

### Архитектура парсера

- Python-сервис (curl_cffi) выделен в отдельный сервис с собственным HTTP API. Laravel job обращается к нему по сети, а не через CLI/shell.
- Очереди — Redis + Laravel Queue. В docker-compose под воркер отдельный контейнер (`queue-worker`), не совмещённый с основным php-fpm/app контейнером.

### Идемпотентность и модель снимков

- Полная версионная история снимков не нужна. Модель: upsert по внешнему id организации/отзыва (без дублей), плюс отдельная таблица-лог `parse_runs` со статусом и метаданными каждого запуска парсинга (без полной копии данных на каждый запуск).
- Повторный парсинг уже существующей в БД организации запускается только вручную (пользователь повторно отправляет ту же ссылку в форме настроек) — никакого автоматического планового перепарсинга (cron) не требуется.

### Защита от бана / антибан-стратегия

- Полноценная ротация прокси и User-Agent, троттлинг под нагрузкой — **не реализуются в коде** в рамках этого срока. Ограничиваемся базовыми паузами между запросами внутри одного прогона парсинга.
- Подход к защите от бана (ротация прокси/UA, паузы, что делать при бане) обязательно подробно описывается в README как задокументированный подход/план, даже если не реализован полностью в коде.

### Обработка ошибок парсера

- Когда парсер ловит бан/капчу от Яндекса или не находит ожидаемый блок разметки (смена вёрстки) — job помечается как `failed` с понятным текстом ошибки, который отображается в UI.
- Автоматических ретраев нет — если запуск не удался, пользователь видит ошибку и решает, пробовать ли снова вручную.

### Стек и инфраструктура

- БД — PostgreSQL (переключение между MySQL/Postgres в Laravel почти не стоит времени, поэтому сразу берём Postgres, без промежуточного варианта на MySQL).
- docker-compose сервисы: `app` (Laravel), `frontend` (Vue), `python-service` (curl_cffi/Playwright), `db` (Postgres), `redis`, `queue-worker` (отдельный контейнер под `php artisan queue:work`).

### Аутентификация

- Страница логина — обычная форма email + password, проверяет seed-пользователя из БД через Sanctum SPA-аутентификацию. Полноценная регистрация/безопасность не требуется, но UX должен выглядеть как настоящий логин.

### Тестирование

- Автотесты в рамках этой задачи не пишутся (приоритет — рабочий парсер и README в условиях сжатого срока).
